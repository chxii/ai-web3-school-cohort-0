## 任务 2：Agent Wallet 权限策略设计

**场景**：以 Web3 Analysis Agent 为场景，假设它在某些高级任务中也需要代用户执行链上动作（如支付分析费用、触发报告存证）。

### 预算（Budget）

- 单次任务最大支出：0.05 ETH
- 每日累计上限：0.2 ETH
- 每月累计上限：1 ETH
- 超出任何一层上限时，任务自动暂停，等待人工批准追加预算
- 预算余额实时记录在链上 Policy 合约中，每次执行前扣减，任务失败后退回

### 可调用合约（Allowed Contracts）

采用白名单机制，只允许调用以下合约：

| 合约地址 | 合约名称 | 允许操作 |
|----------|----------|----------|
| 0xAAA... | EAS AttestationStation | `attest()` |
| 0xBBB... | USDC（on Ethereum） | `transfer()` 且目标地址在白名单内 |
| 0xCCC... | Agent Registry | `registerResult()` |

任何不在白名单内的合约调用，直接被 Guard 拦截，不进入签名流程。

### 可执行动作（Allowed Actions）

| 动作类型 | 是否允许 | 备注 |
|----------|----------|------|
| 读取链上数据 | 允许 | 无需签名，纯查询 |
| 写入链上证明（EAS） | 允许 | 单次 ≤ 0.01 ETH gas |
| USDC 转账（向用户） | 允许 | 仅限退款场景 |
| 调用任意合约 | 禁止 | 白名单外一律拦截 |
| 修改 ERC-20 approve | 禁止 | 高危动作，永久禁止 |
| 部署新合约 | 禁止 | 超出 Agent 职责范围 |
| 治理投票 | 禁止 | 需要独立授权 |

### 人工确认阈值（Human Confirmation Threshold）

以下任意一条触发时，Agent 必须暂停并向用户发送确认请求：

- 单笔金额 > 0.02 ETH
- 目标合约不在白名单（此时直接拒绝，不等确认）
- 24 小时内同类动作执行超过 10 次
- 任务意图描述与实际 calldata 不一致（由链下 policy engine 检测）
- 用户在 Pact 中未明确授权该类型动作

确认超时时间：30 分钟。超时未响应则取消任务并退款。

### 撤销方式（Revocation）

**即时撤销**：用户可随时调用 Policy 合约的 `revokeAgent()` 方法，立即停止 Agent 的所有签名权限，链上生效，不依赖 Agent 配合。

**Pact 级撤销**：每次任务对应一个 Pact，任务结束后权限自动失效，不需要主动撤销。Pact 是临时授权，不是长期权限。

**紧急暂停**：Safe 多签中的任意一个持有人可触发 `pause()`，冻结所有链上动作，等待人工审查后恢复。

**降级回路**：若 Agent 检测到自身行为异常（连续失败、gas 异常消耗），自动触发 `selfPause()`，上报日志，停止执行。

### 日志记录（Logging）

每次执行都记录以下内容：

- 任务 ID、caller DID、时间戳
- 调用合约地址、函数名、calldata hash
- 执行结果（success / failed / rejected）
- 消耗 gas、触发的 policy rule
- 是否经过人工确认，确认时间

存储位置：链下结构化日志（加密存储，用户可导出）+ 链上摘要（每批任务的 Merkle root，防篡改）+ 重要动作附 EAS attestation。

审计接口：用户可通过 Dashboard 查询任意时间段内的执行历史，支持导出 CSV。

### 失败处理（Failure Handling）

| 失败场景 | 处理方式 |
|----------|----------|
| Policy 检查不通过 | 立即拦截，记录原因，不发起签名，退款 |
| 链上交易 revert | 记录 revert reason，gas 损耗说明，部分退款 |
| 用户拒绝确认 | 任务取消，全额退款，记录"用户拒绝" |
| 人工确认超时 | 任务取消，全额退款，无负面记录 |
| Bundler 提交失败 | 重试最多 2 次，仍失败则退款 |
| Agent 服务宕机 | escrow 超时后链上自动退款（不依赖 Agent） |

所有失败都写入链下日志，严重失败（如合约调用白名单外地址被阻断）触发告警通知用户。

## 任务 3：ERC-4337 / Safe / Guard-Policy 为什么重要

### ERC-4337（账户抽象）

解决的核心问题：传统 EOA（外部账户）的签名逻辑固化在协议层，任何转账都必须用私钥签名，无法内置规则。ERC-4337 引入智能账户，把"验证逻辑"搬到合约里，让账户本身可以定义"什么样的签名才算合法"。

对 Agent 场景的意义：
- Agent 可以作为一个授权签名者，但账户合约可以限制它的权限（只能调用特定合约、只能花特定额度）
- 不需要把完整私钥给 Agent，而是给它一个受限的"子签名权限"
- 支持 Paymaster（代付 gas），Agent 执行时不需要持有 ETH，降低资产暴露风险
- 支持批量操作（一个 UserOperation 里执行多步），减少链上交互次数

解决的风险类型：私钥全权限暴露风险、单点控制风险、无法灵活撤销授权的风险。

---

### Safe（多签智能账户）

解决的核心问题：单一签名者控制的账户，一旦私钥泄漏或 Agent 被劫持，资产全失。Safe 要求多个签名方共同批准（如 2/3 多签），任何单点被攻破都不影响资产安全。

对 Agent 场景的意义：
- Agent 是其中一个签名者，但它单独无法完成交易，必须配合另一个人类签名者或第二个 Agent
- 适合团队/机构场景：Agent 负责日常执行，人类保留最终否决权
- Safe 的模块系统允许给 Agent 安装"受限执行模块"，在不动主签名逻辑的情况下给 Agent 开一个受控入口

解决的风险类型：单签名者失控风险、Agent 被劫持后全权操控资产的风险。

---

### Guard / Policy 机制

解决的核心问题：多签和账户抽象只管"谁有权签名"，但不管"签了什么内容是否合理"。Guard 是在交易执行前/后插入的检查钩子，Policy 是一套规则引擎，两者合力实现"有权签名，但签的内容必须符合规则"。

具体能做什么：
- 执行前检查：目标合约是否在白名单、金额是否超限、频率是否异常
- 执行后检查：实际消耗的 gas 和资源是否在预期范围内
- 动态规则：规则本身可以升级（通过治理或多签），不需要换账户

对 Agent 场景的意义：这是实现"任务级授权"（Pact）的关键机制。Agent 的权限不是一张长期通行证，而是每次任务生成一个临时 Pact，Guard 在执行时核验这个 Pact 的边界（预算、合约范围、时间窗口），超出边界直接拦截。

解决的风险类型：授权范围蔓延风险（Agent 做了超出授权的事）、长期权限累积风险（Agent 权限越来越大无法收回）、链上动作不可预期风险。

---

**三者的关系一句话总结**：

ERC-4337 解决"账户本身能不能编程"，Safe 解决"谁有权控制这个账户"，Guard/Policy 解决"合法的签名者能签哪些内容"。三层叠加才能构成对 Agent 链上行为的完整约束，缺任何一层都会留下攻击面。
