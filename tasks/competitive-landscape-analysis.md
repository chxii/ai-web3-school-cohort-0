# 现有解决方案分析：Verifiable Web3 Research Agent 竞品图谱

> 文档目标：梳理截至 2026 年 6 月，与"链上事实可验证 AI 研究 Agent"方向直接相关的
> 已有解决方案，厘清各方的能力边界与空白区，为本项目差异化定位提供分析依据。

---

## 分析框架

围绕本项目的核心需求路径，将市场现有方案分为五层：

```
用户输入（自然语言问题或传言）
     ↓
[层 1] 信息聚合层    — 抓取和索引 Web3 信息
     ↓
[层 2] 链上数据层    — 查询和解析链上原始数据
     ↓
[层 3] 实体识别层    — 将地址映射为可理解的实体
     ↓
[层 4] 研究推理层    — 多步推理、交叉核验、结论生成
     ↓
[层 5] 可溯源交付层  — 结论与证据来源的强绑定、可独立验证
```

现有解决方案各自只覆盖其中 1–2 层。本文档按"层"归类分析，
最终指出空白集中在哪里。

## 一、Dune Analytics + 官方 MCP（链上数据层）

**性质：** 链上数据仓库 + Agent 接入基础设施  
**定位层：** 层 2（链上数据查询）

### 解决什么问题

Dune 是目前覆盖最广的链上数据分析平台，索引超过 130 条区块链的原始交易记录、解码后的智能合约事件、协议分析数据集和社区构建的查询表（Spellbook）。

<2026 年 3 月，Dune 正式发布官方 MCP Server。>其核心能力在于：AI Agent 可通过自然语言驱动完整的数据工作流——表发现、SQL 生成、查询执行、结果可视化——通过单一端点完成，无需人工写 SQL。官方 MCP 暴露 12 个工具，与 Claude、Cursor、ChatGPT 等主流 MCP 客户端兼容。

两周后，Dune 进一步发布了 CLI + Skills.md 框架，允许 AI Agent 通过终端直接访问链上数据，输出标准 JSON 格式，专为机器解析设计（而非人类阅读）。这被定位为"agent-native"的数据基础设施。

同期 Dune 进行了 25% 裁员，CEO 明确表示原因是 Dune MCP 使团队无需 SQL 专家也能构建 Dashboard，标志着其产品战略正式转向 AI 驱动的数据层。

### 边界是什么

**Dune 是数据仓库和查询执行引擎，不是研究 Agent。** 其具体边界：

- **无主动研究规划能力。** Dune MCP 响应的是"执行一个查询"的指令，它不会主动拆解"这个传言涉及哪些地址、需要查什么数据"的问题。研究规划必须由外部 LLM 驱动。
- **SQL 生成准确率依赖上层模型。** Dune 本身不做 SQL 生成，生成 SQL 的是外部 LLM（Claude、GPT 等）。Dune 的 Spellbook Schema 极为复杂（数百张表，多链命名规范不统一），自然语言转 SQL 的准确率在复杂查询场景下不稳定，容易找错表名、字段类型报错或返回空结果。
- **无治理数据。** Dune 索引的是链上执行数据（交易、事件），不索引 Forum 讨论、提案文本、投票理由等治理层信息。
- **无交叉核验层。** Dune 返回的是结构化数据（CSV/JSON），它不做"将此数据与某传言文本进行对比，得出核查结论"的判断。
- **无证据溯源绑定。** 查询结果返回后，Dune 不提供任何机制将该结果"绑定"到某个结论节点，使其成为可追溯的证据引脚。

### 还缺什么

- **研究意图理解层：** 从"一句传言"中提取出需要查询什么数据、查哪条链、查哪个地址段。
- **跨源交叉对比层：** 将链上数字与定性文本描述做语义对齐（"传言说每日转出 500 ETH"对比"实际 48h 转出 23 ETH"）。
- **结论-证据强绑定机制：** 让报告中每一个数字都强绑定到对应的 Query ID 和区块范围，使第三方可以独立重跑验证。
- **自愈能力：** 当 SQL 报错时，Dune 不做任何处理，直接返回错误。如何基于报错信息注入修复上下文并重试，需要外部系统设计。

## 二、Arkham Intelligence（实体识别层）

**性质：** 链上地址去匿名化与实体归因平台  
**定位层：** 层 3（实体识别）

### 解决什么问题

Arkham 的核心产品是其私有 AI 引擎 **Ultra**——一个持续运行的机器学习系统，将链上钱包地址与真实世界实体（机构、个人、协议国库、交易所热钱包等）进行自动归因。截至 2026 年 3 月，其实体数据库已覆盖 **80 万个不同实体**，标签数量超过 8 亿，覆盖 Ethereum、Solana、Base、Arbitrum 等 12 条主链。

对"链上传言核查"场景而言，Arkham 的价值非常具体：当用户说"某 Layer2 协议团队在转出资金"，第一步需要确定"团队钱包"对应哪些地址。Arkham 的 Ultra 引擎可以将协议名称映射为其已知的关联多签地址、国库地址、团队钱包地址。这是其他工具无法替代的能力。

平台对个人用户免费，凭借此策略已积累 300 万注册用户（2026 年 2 月数据）。API 接口支持开发者直接接入 Ultra 查询结果，且在 2025 年下半年更新了支持与 Claude 等 AI Agent 直接集成的文档。

### 边界是什么

- **归因来源不透明。** Ultra 的核心竞争力是其私有归因逻辑，但其具体归因依据（链上聚类、链下数据、用户提交）对外不可见。这意味着结论"地址 0xABC 属于 Protocol XYZ"本身是一个黑盒断言，研究者无法独立验证这个归因的依据链。
- **静态实体库，无动态研究规划。** Arkham 告诉你"谁的地址是谁"，但它不会主动说"这个传言你应该查哪些地址"。研究意图的理解和查询路径规划不在其范围内。
- **无链上数据深度分析。** Arkham 可以显示一个地址的转账记录，但不提供聚合统计（"过去 48 小时净流出量"）、时间序列分析、跨协议对比等 Dune 级别的定量分析能力。
- **无治理数据和定性文本。** Arkham 的数据层完全是链上交易，不涉及 Forum 讨论、提案文本、社区信号。
- **Intel Exchange 的激励结构引入可信度质疑。** Arkham 的情报市场允许用户提交归因数据换取奖励，这在理论上引入了提交虚假归因获利的动机，使部分标签的可信度存在争议。

### 还缺什么

- **归因推导路径透明化：** 用户应能看到"这个地址被归因给某实体的依据是什么"，而不只是结论。
- **归因 + 分析的无缝连接：** 识别出地址后，还需要一个研究层将"是谁的地址"与"这个地址最近做了什么"连接成完整的研究结论。
- **与治理数据的联动：** 一个 DeFi 协议的地址行为往往与其治理提案直接相关，但 Arkham 与 Tally/Snapshot 的数据之间没有任何联动。

## 三、Kaito AI（信息聚合层）

**性质：** Web3 垂直 AI 信息平台（InfoFi）  
**定位层：** 层 1（信息聚合）

### 解决什么问题

Kaito 解决的是 Web3 信息碎片化问题。加密信息散落在 Twitter/X、Discord、治理论坛、研究报告、播客、会议记录等大量非结构化来源中，传统搜索引擎无法有效索引。Kaito 使用 LLM 索引数千个 Web3 数据源，提供可搜索的结构化智能：通过 MetaSearch 功能，用户可以即时检索任何代币、话题或趋势，获取从多个高质量来源聚合的实时洞察。

Kaito 的产品组合（截至 2026 年 6 月）包括：Kaito Pro（机构研究终端）、Kaito Studio（创作者-品牌市场）、Capital Launchpad（融资平台）、Attention Markets（与 Polymarket 合作的注意力预测市场）。

### 边界是什么

- **无链上数据接入能力。** Kaito 的所有数据来源是文本类信息（社交媒体、论坛、文章），它不读取链上交易记录、DEX 数据、钱包余额等链上原始数据。这意味着 Kaito 无法回答"这个地址实际转出了多少钱"这类问题——它只能告诉你"Twitter 上有人说这个地址转出了很多钱"。
- **信息聚合 ≠ 事实核查。** Kaito 的设计目标是"让你更快发现信息"，而非"核验某条信息是否属实"。它不对信息来源进行真伪判断，大量索引内容本身就是未经核实的观点、谣言或营销内容。
- **结论无可追溯证据链。** Kaito 返回的是带引用来源的摘要文本，但这些引用是社交媒体帖子或新闻文章，本身同样可能是二手信息甚至错误信息，不构成链上铁证。
- **Yaps 项目已于 2026 年 1 月关停。** 原因是 X（Twitter）撤销了对"奖励发帖"类应用的 API 访问权限，这对 Kaito 的数据来源构成了重大冲击，削弱了其社交媒体覆盖能力。
- **面向机构，散户可及性受限。** Kaito Pro 的定价和功能面向专业机构用户，散户研究者使用门槛较高。

### 还缺什么

- **链上数据交叉核验层：** 在发现"某传言"之后，能立即调用链上数据对其进行量化核查，而不只是提供"更多关于这个话题的文章"。
- **研究结论可信度分级：** 区分"这是链上铁证支撑的结论"与"这是多个信息源的共识观点"，而不是将两者一视同仁地呈现。
- **可审计的推理路径：** 用户应能看到 AI 从哪些原始来源、通过何种推理步骤得出某个结论，而不只是看到最终摘要。

## 四、Nansen AI（智能资金追踪层）

**性质：** 链上钱包智能分析平台（含 AI Chat 功能）  
**定位层：** 层 2–3（链上数据 + 实体识别，聚焦"聪明钱"维度）

### 解决什么问题

Nansen 的核心能力是**"聪明钱"（Smart Money）追踪**：通过机器学习对超过 2.5 亿个链上钱包操作进行标签化，识别历史上盈利表现优异的钱包地址，并允许用户实时跟踪这些地址的买入、卖出、质押或流动性提供行为。

2026 年 4 月，Nansen 引入了基于 x402 协议和 PayAI 基础设施的**按调用付费（pay-per-call）模式**，允许用户以 USDC 微支付的方式即时查询钱包洞察、代币流向和聪明钱信号，无需月度订阅——这是针对 AI Agent 构建者的重大改进，解决了传统 API 订阅对不确定使用量场景不友好的问题。

Nansen 还提供了 **Nansen AI**（AI 对话查询功能），用户可以用自然语言提问，获取实时链上数据的即席分析。

### 边界是什么

- **聚焦"谁在交易"，不聚焦"某传言是否属实"。** Nansen 的设计逻辑是"跟随聪明钱做决策"，其数据和工具围绕交易信号优化，而非围绕"核查某个特定断言的真实性"。
- **无治理数据维度。** Nansen 不索引 DAO 提案、投票记录或 Forum 讨论，无法回答"这个提案通过后谁获益"等治理分析问题。
- **Nansen AI 的回答缺乏可审计推理路径。** 其 AI Chat 功能返回的是直接结论，不展示查询了哪张表、用了什么 SQL、原始数据是什么——用户只能相信结论，无法独立验证。
- **标签体系不透明。** "Smart Money"标签的认定标准是 Nansen 的私有算法，用户无法知道某个地址被打上"Smart Money"标签的具体依据，这对研究场景构成可信度隐患。
- **高订阅价格限制散户访问。** Pro 计划约 $999/月，对独立研究者而言几乎不可及。虽然新推出了 pay-per-call 模式，但这更面向 Agent 开发者而非终端研究用户。

### 还缺什么

- **"为什么得出这个结论"的完整推理路径：** 链上数据分析结论必须能追溯到具体的 SQL 查询和原始返回数据，而不只是 AI 的口头摘要。
- **多源数据的交叉融合：** 将链上钱包行为（Nansen 所做的）与治理提案文本（Tally/Snapshot）、社交媒体传言进行联合分析，目前没有任何工具做这件事。

## 五、通用 AI 研究工具：Perplexity Deep Research / ChatGPT Deep Research（基线对比）

**性质：** 通用 AI 搜索与深度研究工具  
**定位层：** 层 1 + 层 4（信息聚合 + 通用推理），缺失层 2、3、5

### 解决什么问题

Perplexity Deep Research 和 ChatGPT Deep Research 是目前最贴近"AI 自动研究"体验的通用工具。Perplexity 以"来源优先"架构著称，在 OpenAI SimpleQA 基准上达到 93.9% 的准确率，每份报告引用 50+ 来源，完成速度 3 分钟内。ChatGPT Deep Research 则擅长长篇分析和复杂推理链。

### 边界是什么（Web3 研究场景中的根本性局限）

这两个工具在 Web3 研究场景中面临的问题不是产品细节问题，而是**架构性缺陷**：

**缺陷一：爬取 Web 内容 ≠ 查询链上事实。**  
Perplexity 和 ChatGPT Deep Research 的数据来源是互联网上的公开页面——新闻文章、Twitter 帖子、博客、论坛。这些内容本身就充满了未经核实的链上传言。当用户问"某协议团队是否在砸盘"，这两个工具只会搜索"有没有人写过这个话题的文章"，而不会去查询链上真实转账记录。

**缺陷二：二手幻觉（Second-Hand Hallucination）问题。**  
研究已记录了一种特定的 Perplexity 幻觉模式：Perplexity 检索到的网页本身就包含 AI 生成的或事实错误的内容，Perplexity 再将这些错误以"有引用来源"的形式重新呈现。引用 URL 真实存在，但原始来源本身就是错的。在 Web3 场景中，大量"分析文章"本身就是基于链上数据的错误解读，这个问题尤为严重。

**缺陷三：引用的是"有人说了什么"，而非"链上实际发生了什么"。**  
即使 Perplexity 引用了一篇 Nansen 或 Dune 的截图，它引用的是文章发布时的数据快照，而不是实时链上数据。用户无法确认这个数字在报告完成时是否仍然准确，也无法用相同的查询参数重跑验证。

**缺陷四：无自主多步工具调用能力。**  
Deep Research 的信息获取是"搜索网页"，不是"调用区块链 API 执行 SQL 查询并分析原始 JSON"。它不能：识别一条传言涉及的链上地址 → 调用 Dune 查询该地址的转账记录 → 对比传言数字与链上实际数字 → 得出有据可查的核查结论。

### 还缺什么

- **链上数据直接查询能力**（对接 Dune MCP 而非搜索二手分析文章）
- **链上原始数据 → 结论的完整证据路径**
- **研究结论的独立可重跑验证机制**

## 核心结论

**没有任何一个现有工具或工具组合同时具备以下四种能力：**

1. **自然语言驱动的多步研究规划**（而非单次问答）
2. **实时链上原始数据查询**（而非二手文章引用）
3. **定性传言与链上定量数据的自动交叉核验**
4. **每条结论强绑定可独立重跑的链上证据引脚**

这四点的组合，就是本项目存在的根本理由。

现有工具的最大公约数是"看别人的分析"，而本项目要做的是"让 Agent 像链上分析师一样去跑数据、得出结论、并证明结论的来源"。这两者之间，是质的差异，而非量的差异。

## 六、Claude Code + MCP 生态 + Skills（通用 Agentic 平台）

**性质：** Anthropic 出品的 Agentic 编程助手，具备完整工具调用、MCP 接入与可扩展 Skills 体系  
**定位层：** 平台级基础设施（层 1–4 均可触达，但需自行配置）

### 解决什么问题

Claude Code 是目前生产级 Agentic 工具中生态最完整的一个。它运行于终端，同时支持 VS Code、JetBrains、桌面应用、Web 端和 CI/CD 流水线，核心能力是直接访问文件系统、运行 Shell 命令、浏览网页和调用外部 API，这些内置能力构成 Agent 的基础，而 Skills、MCP、Hooks 和子 Agent 作为扩展层叠加其上。

其扩展体系对本项目场景尤其相关。实用的 Claude Code 配置分为五层：CLAUDE.md（项目规则）、MCP 服务器（外部工具与数据）、Skills（可复用工作流）、Hooks（自动化与安全检查）、以及子 Agent（隔离的研究或审查任务）。

在 Web3 场景下，技术上完全可以组合出一个能力接近的链路：通过 Dune MCP 集成，Claude 可以将 execute_query、get_execution_result 等 Dune API 端点作为原生工具调用，开发者只需说"分析 Base 链上这个钱包地址"，Agent 就会调用正确工具、以 Wei 格式取回数据并格式化输出结果，像一个自主运行在终端里的区块链浏览器。

Skills 体系进一步降低了重复性工作的门槛。Skills 通过包含 SKILL.md 文件的目录来定义，支持预置 Skills 和自定义 Skills，后者在整个工作区内共享，所有成员均可访问。不仅如此，Agent SDK 将 Claude Code 同款的工具、Agent 循环和上下文管理能力开放为 Python/TypeScript 可编程接口，开发者可以自主构建能够读取文件、运行命令、搜索网页和编辑代码的 AI Agent。

### 边界是什么

**Claude Code + Dune MCP + Skills 的组合是平台，而非产品。** 其核心边界如下：

**边界一：工具调用不等于研究规划。** Claude Code 在接到"查一下某传言是否属实"时，会试图理解并执行，但它的自主研究规划逻辑完全依赖通用 System Prompt 和 CLAUDE.md 中的规则——没有专门为"Web3 谣言核查"设计的任务拆解框架。它的推理路径不是"意图 → 研究假设 → 数据需求 → 工具调用序列"，而是更通用的"任务 → 工具调用 → 输出"。

**边界二：没有 Evidence Pin 架构。** Claude Code 的输出是终端文本或文件，工具调用的原始返回数据（Dune JSON、Tally 提案 API 响应）不会被自动结构化存储、标注时间戳/区块范围、并绑定到某个结论节点。数据用完即丢，无法事后点击追溯。

**边界三：自愈机制是通用代码层面的，不是 Web3 SQL 层面的。** Claude Code 在遇到报错时会自主重试，这是其标志性能力。但它的错误修复上下文来自通用编程知识，而不是 Dune Spellbook 的具体 Schema（哪些表在哪条链上、字段命名规范、decoded 表的结构）。对复杂 Web3 SQL 报错的修复能力，远不如注入了专属 Schema 字典的专用 Agent。

**边界四：没有可视化研究图谱输出。** Claude Code 的交付物是终端输出、文件或代码，没有任何内置机制将研究过程渲染为可交互的节点图谱。

**边界五（赛道硬约束）：** Claude Code 绑定 Anthropic 的 Claude 模型，无法用 GLM-5.1 驱动其核心 Agent 循环。这在本次 Hackathon 赛道规则下是根本性的不可替代点。

### 还缺什么

- **Web3 研究意图的领域专用解析层**：将"传言文本"结构化为"研究假设 + 数据需求清单 + 目标链 + 时间窗口"。
- **Evidence Pin 持久化存储与绑定机制**：每条工具调用结果必须自动归档并绑定为可追溯引脚。
- **Research Graph 可视化层**：Research 过程的图谱化渲染，超出任何现有 Skill 的覆盖范围。
- **Dune Schema 域知识注入**：当 SQL 失败时，注入 Spellbook 合约字典辅助修复，而非依赖通用代码错误理解能力。

## 七、Hermes Agent + MCP（开源自改进 Agentic 框架）

**性质：** NousResearch 出品的开源自主 Agent 框架，支持持久记忆与技能自创建  
**定位层：** 平台级基础设施（与 Claude Code 类似，但模型无关、更侧重自改进）

### 解决什么问题

Hermes Agent 是一个开源自主 AI Agent，由 Nous Research 于 2026 年 2 月发布。它不是绑定 IDE 的编程副驾，也不是围绕单一 API 的聊天机器人包装——它运行在你的服务器上，记住自己学到的内容，并随着运行时间越长而变得越来越有能力。

其区别于其他开源 Agent 框架的核心特性是**自改进机制**：Hermes Agent 配备了"Agent 策划式记忆与周期性回顾"功能，Agent 会反思自己的工作，筛选值得保留的记忆，并在面对困难问题时主动创建新的 Skill 文档——且每次使用时还会迭代优化已有的 Skill。

对 Web3 场景的相关性体现在其生态的快速扩展上：社区生态在六周内已涌现出多个跨领域项目，其中 hermes-blockchain-oracle 是专为 Solana 链上智能数据打造的 MCP 服务器，与 Hermes Agent 深度集成。其 MCP 支持与 Claude Code 同等级别：通过在配置文件中添加 MCP 服务器地址，即可接入 GitHub、数据库、云基础设施、监控系统等任何暴露 MCP 端点的服务，MCP 生态每增加一个新服务器，Hermes Agent 无需任何代码改动即可立即使用。

### 边界是什么

**边界一：技能无签名溯源，不适合"可验证"研究场景。** 这是 Hermes Agent 用于本项目时的致命伤。Skill 文件不携带签名溯源信息，Agent 自己生成的 Skill 和用户手动放入目录的 Skill 之间没有任何可观测的区别。而且 Skill 文件中可能包含 Agent 从敏感任务中提炼的样本和上下文数据。这与本项目"每条结论都可独立验证来源"的核心设计原则背道而驰。

**边界二：自改进是任务泛化的，不是 Web3 研究专化的。** Hermes 的自改进逻辑是"遇到困难问题时创建通用解法 Skill"，而非围绕特定领域（如 Dune SQL Schema、链上地址归因、治理提案解析）构建领域知识。Agent 通过记忆提升的是任务完成效率，而非链上研究的专业深度。

**边界三：底层模型质量不确定性高。** Hermes Agent 支持 OpenAI、Anthropic 和本地 Ollama 模型，你自带 API Key——文档中坦诚说明它仍处于早期阶段，文档有空白，可靠性因配合的模型后端不同而差异显著。对比之下，GLM-5.1 在 MCP-Atlas 工具调用基准上有明确的 71.8 分作为质量保证。

**边界四：无研究图谱输出层。** 与 Claude Code 相同，Hermes Agent 的交付物是文本输出和 Skill 文件，没有将研究推理路径渲染为可交互图谱的内置机制。

**边界五：安全与审计设计不成熟。** 目前 Skill 的签名溯源、审批工作流和审计追踪等生产级特性均尚未解决，作者明确表示不建议将其用于受监管的后端工程场景。虽然这对 Hackathon Demo 影响较小，但对"可验证研究"这一核心价值主张而言，框架本身的不可验证性是一个显著的概念矛盾。

### 还缺什么

- **Skill 的可签名溯源机制**（这与 Evidence Pin 的设计理念完全一致，但 Hermes 目前没有）
- **Web3 研究专化的 Skill 库**（hermes-blockchain-oracle 只是开始，还没有 Dune 深度查询 + 治理数据联合分析 + 传言核查的完整 Skill 链路）
- **Research Graph 渲染输出**
- **与本赛道的模型绑定问题**：Hermes Agent 可以接 GLM-5.1 作为后端（支持任意 OpenAI-compatible 端点），但整个工具链的提示词优化和 Skill 生态仍围绕 Claude/GPT 建立，接入 GLM-5.1 后的实际效果需要重新验证。

## 平台 vs 产品：最关键的竞争维度重新界定

加入 Claude Code 和 Hermes Agent 之后，竞争格局的本质变得更清晰：

**Claude Code + MCP + Skills 和 Hermes Agent + MCP 是平台，不是产品。** 它们提供的是"任何工具都可以调用"的通用能力，而非"Web3 研究可验证性"这一特定问题的解决方案。

类比来说，这就像"Excel 可以做财务模型"和"Bloomberg Terminal 是专业金融工具"之间的区别——前者是通用平台，理论上什么都能做；后者是围绕特定领域需求设计的专用产品，在该领域的深度、可靠性和用户体验上不可替代。

本项目相对于平台级竞品的差异化，集中在以下三个**需要专门设计**、任何现有 MCP 或 Skill 都不提供的能力：

```
① Web3 谣言→研究假设→数据需求 的领域专化解析
   （不是"给我查一下"，而是"从传言文本提取需核查的链上断言"）

② Evidence Pin 持久化 + 结论强绑定架构
   （不是"工具调用完成后输出文本"，而是"每条数据自动归档并打上区块范围锚点"）

③ Research Graph 的实时渐进渲染
   （不是终端日志，而是每个评委都能当场点击验证的可交互知识图谱）
```

这三个能力，写一个 SKILL.md 是做不到的。它们需要专门的系统架构设计。这正是本项目存在的核心理由。
